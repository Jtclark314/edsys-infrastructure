# Observed S3 compatibility boundary

Live commissioning on 2026-11-12 tested SeaweedFS 4.53 through its private S3 API.
A synthetic JSON object uploaded under a `.json` key with the explicit
`Content-Type: application/octet-stream` was returned as `application/json`.
The content bytes, metadata and tags still matched, but the strict restore
helper rejected the changed content header. The disposable bucket was removed.
This is an observed API behavior, not merely a difference in the admin UI.

The migration and both restore verifiers require exact content headers,
metadata, tags, object roster and SHA-256 of actual payload bytes. Do not waive
the header check or treat ETags as content verification. If a real application
object encounters this behavior, stop promotion and resolve the compatibility
decision while preserving the original MinIO data.

S3-managed response values such as `LastModified`, ETags and request IDs are
regenerated by API copies/restores. The migration ledger retains the source
listing fingerprint, and logical exports retain observed timestamps/ETags for
provenance; neither is a promise to set a server-generated timestamp through
`PutObject`. Payload verification uses actual SHA-256, independent of ETags.

The original source also had empty notification/logging settings and no website
configuration. Non-default settings for those features are explicitly refused
by these helpers, alongside versioned/locked objects, until separately reviewed.

A separate real API restore canary passed for three synthetic objects using
their intended `application/json`, `application/octet-stream` binary and
`text/plain` empty-file content types. It included Unicode/spaces in a key,
cache/disposition/expiry headers, metadata and tags. This proves those cases;
it does not establish full compatibility with every S3 feature or object type.

Raw fixtures, the observed MIME receipt and acceptance receipts remain in the
private task evidence directory outside Git. The final production acceptance
requires full frozen-source reconciliation and an isolated native restore,
followed by Langfuse historical reads and new writes.

The isolated native restore requires an explicit `--network-subnet` to avoid
exhausted default Docker address pools. It accepts a usable RFC1918 IPv4 CIDR,
checks every current Docker IPAM subnet and non-default IPv4 host route for
overlap, and passes the checked CIDR to Docker `--subnet`. A candidate such as
`10.254.249.0/28` must be rechecked at each run; it is not a permanent reservation.
The existing root rehearsal network is a separate `10.254.248.0/24`.

The authoritative commissioning native checkpoint was fully restored for all
142,415 production objects (804,101,811 bytes), and retains one explicitly owned
task-only rehearsal bucket. Restoring that checkpoint with the current verifier
requires `--allow-extra-bucket langfuse-rehearsal-20261112`; an unlisted extra
bucket is refused. After that full proof, the live rehearsal bucket and its 37
objects were deleted. The production roster stayed exact, all seven production
`.dat` files and seven `.idx` files matched the proven checkpoint before and
after cleanup, and authenticated frozen-object reads passed. There was no
second independent full restore after cleanup. Recurring logical exports use
the clean live bucket roster. Private `commissioning-scope.json` records this
boundary alongside the retained native checkpoint.

```sh
sudo python seaweed_checkpoint.py restore --checkpoint /private/stopped-checkpoint \
  --work /private/new-isolated-restore --network-subnet 10.254.249.0/28 \
  --allow-extra-bucket langfuse-rehearsal-20261112
```
